ELBA/WISE Millibottleneck Theory: CloudLab Experiment Setup and Execution Guide

Introduction

It is commonly known that microservice system performance is often limited by the resource bottlenecks in the exeuction path of a request. Instead of a single bottleneck hindering the performance of a system, we observe a theory concerned with the validation of the existence of millibottlenecks. These are transient resource bottlenecks which occur in containers hosting multiple services. They occur so quickly they are often undetectable by traditional resource monitoring tools. These millibottlenecks propogate through the system in undefined ways, leading to long-tail latency on some requests. Company revenue is directly tied to system performance, making these bottlenecks important to understand.

Objectives

In this experiment, we wish to experimentally validate the millibottleneck theory of performance bugs using WISE/ELBA, a toolkit to conduct large-scale system experiments in the cloud.

Prerequisites

Generating an SSH Public Key

Follow these steps to create an SSH public key without a passphrase:

  1. Open a terminal on your computer.
  2. Run the following command to generate a new SSH key pair:
    3. ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
    • -t rsa: Specifies the type of key to create. In this case, RSA is used.
    • -b 4096: Sets the number of bits in the key to 4096.
    • -C "your_email@example.com": Adds a comment to the key, typically your email address, for identification purposes.
  3. When prompted to specify a file to save the key, press Enter to use the default location.
  4. When asked to enter a passphrase, simply press Enter to leave it empty.
    • It is crucial that you do not set a passphrase on your key, as this will prevent it from being used remotely on a host node.
  5. When prompted to confirm the passphrase, press Enter again.
  6. Your SSH key pair is now generated. The private key is stored in ~/.ssh/id_rsa, and the public key is in ~/.ssh/id_rsa.pub.

Confirm the creation of the key by running:

cat ~/.ssh/id_rsa.pub

Add SSH Public Key to GitHub

Once you've generated an SSH key, follow these steps to add it to your GitHub account:

  1. Log in to your GitHub account.
  2. In the upper-right corner of the page, click your profile photo, then select Settings from the dropdown menu.
  3. In the left sidebar, click SSH and GPG keys.
  4. Click the New SSH key button.
  5. In the Title field, add a label for the key.
  6. In your terminal, copy the contents of your public key file by running:
    7. cat ~/.ssh/id_rsa.pub
  7. Paste the copied key into the Key field on GitHub.
  8. Click the Add SSH key button.
  9. If prompted, confirm your GitHub password to complete the process.

You're now ready to use SSH with GitHub! Test your setup by running:

ssh -T git@github.com
  • The ssh command opens an SSH client on your system.
  • The -T flag disables pseudo-terminal allocation, which is necessary since GitHub does not provide shell access.
  • git@github.com specifies the user (git) and the host (github.com) to try and connect to.

If everything is set up correctly, you should see a success message.

Hi <GitHub username>! You've successfully authenticated, but GitHub does not provide shell access.

PACE provides infrastructure, commodity services, software support, technical services, and scalable, shared, compute clusters. This gives Georgia Tech faculty and students access to the tools needed to perform innovative research.

Objectives

On this page, we seek to provide an introduction into working with PACE, as well as draw parallels between PACE and Cloudlab. We will identify tools and technologies that were useful for Cloudlab, and will be useful when the experiment is hosted on PACE.

PACE Architecture

The nodes in PACE are seperated into head nodes and compute nodes. The head nodes are a shared resource that are used to log in to the cluster. They are not used for computation or vizualizations, but are instead good for data management / configuration. The compute nodes are the machines that execute all the computations. They aren't directly accessed by the user, instead they are given jobs by the scheduler as they come in.


This flowchart depicts how compute resources are allocated on the PACE cluster. Depending on the specified machine make and model in the salloc or sbatch request, you will be allocated these resources. Each hardware type, CPU or GPU has a default machine that jobs will spillover on to if the requested machine is unavailable. This happens without any user action. This allows for a fair use of shared resources. All the user needs to do is specify the needed number of CPUs, GPUs, memory, walltime, and any specific hardware resources. As the resources become available, they will be allocated for the user's jobs for as long as requested in the job submission.

  • Phoenix

  • Hive

    • Hive is a newer cluster within PACE, added after grant was awarded by the NSF for use in research regarding astrophysics, computational biology, health science, chemistry, materials and manufacturing, and more.

This cluster allows graduate and undergraduate students the opportunity to gain experience in a high performance computing environment and have access to the tools that researchers at the institution use.

QoS and the Slurm Scheduler

Within the Phoenix and Firebird clusters, jobs are submitted to one of two services levels that span the entire cluster. The default level is inferno, but when that is overloaded there is a backfill level called embers.

Inferno: Primary QoS

  • Base Priority: 250,000
  • Max jobs per user: 500
  • Max eligible jobs per user: 500 (10 for GPU jobs)
  • Wallclock limit: 21 days (3 days for GPU jobs)
  • Jobs charged to the provided account

Embers: Backfill QoS

  • Base Priority: 0
  • Max jobs per user: 50
  • Max eligible jobs per user: 1
  • Wallclock limit: 8 hours
  • Preemption after 1 hour
  • Jobs not charged to an account

Additional Constraints on Running Jobs

  • Per-account processors: 6000 (Inferno only)
  • Per-user GPUs: 32 (Inferno only)
  • Per-account CPU-time: 300,000 CPU-hours (including Embers jobs)

Modes of Operation

The SLURM (Simple Linux Utility for Resource Management) is a resource management tool that has integrated scheduling logic. The implementation that runs on PACE has two modes of operation for submitting jobs, interactive and batch.

Interactive Mode

Allows for interactive use for job creation and submission to the scheduler. The same as accessing any remote workstation and executing a job. Submitted jobs will wait in a queue until resources are available while the user waits in real-time. When resources are available, your job will be submitted to a compute node. Use the salloc command to request an interactive job. The salloc --help command may be of use as well.

Batch Mode

You can submit a job as an sbatch script which waits in a queue until resources are available. Everything runs on its own in the background once a resource is available. The script will include resource requirements, settings, and tasks. Note that if your job requires user interaction, you cannot use batch processing.

MPI Jobs in HPC Environments

MPI (Message Passing Interface) jobs are used in high-performance computing (HPC) to enable parallel processing across multiple nodes. MPI is a message passing standard created for parallel computing systems. It is designed to be portable between different systems. MPI allows tasks to communicate by passing messages, making it suitable for large-scale simulations and computations that require significant communication between nodes. Typically, MPI jobs are launched using srun or mpirun commands. The PACE cluster supports the MPI libraries MVAPICH and OpenMPI without needing to install extra packages.

MPI (Message Passing Interface) jobs can be executed in Slurm using srun. This method ensures efficient parallel job execution across nodes.


            # Compile the MPI program
            mpicc mpi_program.c -o mpi_program
            
            # Run the program with 4 tasks and 1 CPU per task
            srun -n4 -c1 mpi_program program_arguments

Array Jobs in HPC Environments

Array jobs allow users to submit multiple tasks with a single job script, often used for running many similar tasks, such as parameter sweeps or batch data processing. Each task runs independently, and they are managed under a single job ID, making monitoring and resource allocation more efficient. Array jobs are typically specified using the --array flag in Slurm.


                #SBATCH --array=1-10
                #SBATCH -o %A_%a.out
                
                # Executes the program with input indexed by SLURM_ARRAY_TASK_ID
                srun myprogram data${SLURM_ARRAY_TASK_ID}

Here, %A is the job ID and %a is the array task ID, which helps organize output files.
