ELBA/WISE Millibottleneck Theory: CloudLab Experiment Setup and Execution Guide

Introduction

It is commonly known that microservice system performance is often limited by the resource bottlenecks in the exeuction path of a request. Instead of a single bottleneck hindering the performance of a system, we observe a theory concerned with the validation of the existence of millibottlenecks. These are transient resource bottlenecks which occur in containers hosting multiple services. They occur so quickly they are often undetectable by traditional resource monitoring tools. These millibottlenecks propogate through the system in undefined ways, leading to long-tail latency on some requests. Company revenue is directly tied to system performance, making these bottlenecks important to understand.

Objectives

In this experiment, we wish to experimentally validate the millibottleneck theory of performance bugs using WISE/ELBA, a toolkit to conduct large-scale system experiments in the cloud.

Prerequisites

Generating an SSH Public Key

Follow these steps to create an SSH public key without a passphrase:

  1. Open a terminal on your computer.
  2. Run the following command to generate a new SSH key pair:
    3. ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
    • -t rsa: Specifies the type of key to create. In this case, RSA is used.
    • -b 4096: Sets the number of bits in the key to 4096.
    • -C "your_email@example.com": Adds a comment to the key, typically your email address, for identification purposes.
  3. When prompted to specify a file to save the key, press Enter to use the default location.
  4. When asked to enter a passphrase, simply press Enter to leave it empty.
    • It is crucial that you do not set a passphrase on your key, as this will prevent it from being used remotely on a host node.
  5. When prompted to confirm the passphrase, press Enter again.
  6. Your SSH key pair is now generated. The private key is stored in ~/.ssh/id_rsa, and the public key is in ~/.ssh/id_rsa.pub.

Confirm the creation of the key by running:

cat ~/.ssh/id_rsa.pub

Add SSH Public Key to GitHub

Once you've generated an SSH key, follow these steps to add it to your GitHub account:

  1. Log in to your GitHub account.
  2. In the upper-right corner of the page, click your profile photo, then select Settings from the dropdown menu.
  3. In the left sidebar, click SSH and GPG keys.
  4. Click the New SSH key button.
  5. In the Title field, add a label for the key.
  6. In your terminal, copy the contents of your public key file by running:
    7. cat ~/.ssh/id_rsa.pub
  7. Paste the copied key into the Key field on GitHub.
  8. Click the Add SSH key button.
  9. If prompted, confirm your GitHub password to complete the process.

You're now ready to use SSH with GitHub! Test your setup by running:

ssh -T git@github.com
  • The ssh command opens an SSH client on your system.
  • The -T flag disables pseudo-terminal allocation, which is necessary since GitHub does not provide shell access.
  • git@github.com specifies the user (git) and the host (github.com) to try and connect to.

If everything is set up correctly, you should see a success message.

Hi <GitHub username>! You've successfully authenticated, but GitHub does not provide shell access.

Steps to Run the Experiment

1. Check Resource Availability

In CloudLab, ensure that a bare-metal machine with at least 12 free resources is available on CloudLab (e.g., rs620, r350).

2. Create a CloudLab Experiment

Create a new experiment on CloudLab:

Modify the profile.py script to match your experiment's requirements:

  • Set the appropriate hardware type to match the available resource in CloudLab.
  • Adjust the node count to the number of nodes you will allocate in CloudLab
  1. Navigate to the CloudLab Experiments page and create a new experiment profile.
  2. Select Upload File under Source code, and choose your edited profile.py
  3. Select Select Profile and continue through the profile setup process.
  4. Ensure the number of nodes is set to 12 and set the Experiment Duration to at least 4 hours.
After you have completed the setup process, click Instantiate to begin setting up the experiment.

Download the project zip file using the provided link: Download Zip File.

5. Run the Controller Setup Script

Execute the controller_setup.sh script with the appropriate arguments:

                --private_ssh_key_path "/path/to/your/id_rsa" \
                --controller_node your.controller.node \
                --git_email your.email@example.com \
                --swarm_node_number 6 \
                --client_node_number 5

Replace the placeholders with your actual information.

Controller Setup Script Breakdown 


    scp -o StrictHostKeyChecking=no -i ${private_ssh_key_path} ${private_ssh_key_path} ${username}@${controller_node}:.ssh/id_rsa
    scp -o StrictHostKeyChecking=no -i ${private_ssh_key_path} -r socialNetworkLSU.zip ${username}@${controller_node}:socialNetworkLSU

These two lines of the script use scp (secure copy protocol) to copy over your private key and the Social Network zip file to the controller node. You can verify the completion of this step by SSHing in to the controller node and verifying that these files exist on that node. The command to SSH into that node can be found in the CloudLab experiment page. It should look something like ssh {CloudLab_username}@{node_id}.cloudlab.umass.edu 


    ssh -o StrictHostKeyChecking=no -i ${private_ssh_key_path} ${username}@${controller_node} "

This line will open an SSH connection to the controller node. ssh -o StrictHostKeyChecking=no -i ssh opens the OpenSSH SSH client to allow for remote login to the controller node. -o StrictHostKeyChecking=no is used to give options in the format of the SSH config file. StrictHostKeyChecking specifies how host keys are checked during connection and authentication. If it is set to no, the node will accept incoming SSH keys from servers not in the known hosts list. 


    ssh-keygen -F github.com || ssh-keyscan github.com >> ~/.ssh/known_hosts
    echo -e 'Host *\n\tStrictHostKeyChecking no\nHost benchmark\n\tHostName 10.10.1.7\n\tUser ${username}' >> ~/.ssh/config

These two lines deal with configuring the remote node for SSH connections. ssh-keygen -F github.com ssh-keygen is a tool for generating and managing authentication keys. The -F flag specifies a hostname to be searched for in the known host config file. ssh-keyscan If the first command fails (hostname not found in known_hosts), this command is run and appended to known_hosts. ssh-keyscan retrieves the ssh host keys for GitHub. The second line adds the text in quotes to the ssh config file on the controller node. This disables strict key checking for all hosts. Then it specifies a host configuration for the 'benchmark' host and specifies an IP address and username. 


    sudo sh -c \"echo 'Host *\n\tStrictHostKeyChecking no' >> /root/.ssh/config\"

This line executes a shell as root user and runs the string as a command in that shell. This modifies the ssh config for the root user in a similar way as above. 


    git config --global user.email ${git_email}
    git config --global user.name ${username}
    git config --global core.editor "vim"
    git clone git@github.com:WindowsXp-Beta/SocialNetwork.git SetupScripts
    unzip socialNetworkLSU

This block of code configures git on the remote node using your git_email and username. Then, the appropriate repository is cloned from GitHub on to the controller node as the SetupScripts repository. The setup socialNetworkLSU zip file we copied to the controller node is now unzipped. 


    sudo apt-get update
    sudo apt-get install -y python3-pip maven pdfgrep

sudo apt-get update updates the local package index with the latest verison of available packages for the given OS. This way the package list is up to date before installing any libraries. This requires root permissions. sudo apt-get install -y python3-pip maven pdfgrep installs multiple system wide packages, which requires root permissions. pip is a package manager for python. Maven is a build automation tool for Java projects, which is necessary to setup the rubbos workload generator for the client nodes. This is required because Rubbos is implemented using Java servlets, which send HTTP requests to the microservices nodes upon command from the controller node. pdfgrep is a command line tool for searching PDF files for text strings. 


    cd SetupScripts
    pip3 install -r requirements.txt
    python setup_docker_swarm.py -a 10.10.1.1 -n ${swarm_node_number} -cn ${client_node_number}

This block of code enters the SetupScripts directory, which is where we cloned the SocialNetwork repository. Then it uses pip to install all necessary python packages for the project, which is defined in requirements.txt. This is standard practice for ensuring that all the necessary dependencies are tracked in a centralized file. Then the setup_docker_swarm.py script is executed. This script takes in the ip address of the managing node, the number of swarm nodes used to host the microservices, and the number of client nodes used to send requests to the SocialNetwork application. This script is complex and a large part of executing the SocialNetwork benchmark, so it has been given a section at the bottom of the site where it's components are explained. 


    cd ~/DeathStarBench/socialNetwork
    source set_elba_env.sh
    ./scripts/CONTROL_exec.sh

This navigates into the newly cloned DeathStarBench/socialNetwork directory (done in setup_docker_swarm.py) and attempts to run two scripts. source set_elba_env.sh runs the set_elba_env script in the current shell environment. This means that any variables or functions that are defined in the script are available in the current shell session once the script is finished. ./scripts/CONTROL_exec.sh executes the controller script. The capitalized name is a convention to indicate that this a main control script for the application. 


    sudo cp /users/${username}/scripts_limit/generateResult.sh /users/${username}/socialNetwork/
    sudo apt install -y python2

This block copies the generateResult.sh script from the scripts_limit directory into the socialNetwork directory that we recently cloned. Then it installs python2 on the controller node which enables the execution of legacy components not compatible with the newer version of Python. 


    cd /users/${username}/socialNetwork/
    ./generateResult.sh &> output.log

The block changes the current directory and executes the recently copied over script. The output of this script is then redirected to the output.log file. The &> operator is used in bash scripts to route both the standard output and the error output into a file.

6. Start the Experiment via JobManager

Ensure Python 3 is installed on your local machine. Run the JobManager script: 

python3 JobManager.py

When prompted, enter the required information:

  • CloudLab Username: (e.g., username)
  • Path to Private SSH Key: (e.g., /Users/username/.ssh/id_rsa)
  • Hostname of Controller Node: (e.g., apt186.apt.emulab.net)
  • GitHub Email Address: (e.g., your.email@example.com)
  • Number of Swarm Nodes: (e.g., 6)
  • Number of Client Nodes: (e.g., 5)

You can add multiple experiments or proceed to configure the current one.

Configure Experiment Files

The script will open several configuration files in a terminal editor:

  • config/config.json
  • Docker Swarm template
  • Dedicated scripts

config/config.json

{ "username": "$your_cloud_lab_username", "experiment_name": "$username-six_digit_number", "ssh_host": "$host_ssh_name" }

This is the configuration file that was edited prior to running the controller script. Confirm that these values are accurate and then use CTRL + O to bring up the save prompt. Then hit enter to save, and CTRL + X to exit.

socialNetwork/docker-compose-swarm.yml.template

This is a template file used for configuring Docker Swarm deployments, which in this case are the containers hosting services from the application. In this file you must replace all instances of <<EXPERIMENT_NAME>>, <<SSH-HOST>>, and <<USERNAME>> with the appropriate values. These are your cloudlab experiment name, the SSH host from config.json, and your cloudlab username. In addition to this, you must determine whether or not 'infosphere' is correct. 'infosphere-pg0' is also a correct hostname, and it is determined by the nodes you have provisioned. This can be determined by connecting to each node via SSH and then executing the hostname command.

dedicate.sh

This script allocates CPU cores on each swarm node for each service container. This gives precise control over which core is running which process, and makes sure compute resources are isolated. Interestingly, some containers are given a single core to run on, while some services are given multiple cores. This might indicate that some services are multithreaded or require more compute resources. Further examination of the source code for each container will yield more information.

Use the editor to adjust the configurations as needed. Save and exit each file to continue.

Confirm all information and start the experiment when prompted.
